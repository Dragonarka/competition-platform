## What Went Well

1. **Clean, concise epic with clear scope boundaries.** Three stories, zero overlap, zero scope creep. Story 6.1 owned standings, 6.2 owned bracket, 6.3 owned presenter. Each story knew exactly what to leave alone. The planning was tight and the implementation followed it precisely.

2. **SSR + client-island pattern established and proven reusable.** Story 6.1 did the hard work — chose the HTTP-fallback path (`httpBatchLink` from `trpc-server.ts`), established the `createServerTrpcClient()` utility, proved `useQuery({ initialData })` hydration works. Story 6.2 followed the pattern identically. This is now a proven, repeatable architecture for any public SSR route.

3. **Adversarial review gate caught 3 HIGH findings.** All would have been user-visible bugs:
   - 6.1 H1: Broadcast sites called `computeStandings` without enrichment — WebSocket payloads would have been missing `criteriaBreakdown`/`groupBreakdown` data.
   - 6.2 H1: Bye slot B had `isBye` hardcoded to `false` — byes would have shown as regular matchups.
   - 6.3 H1: Unsafe `as` cast on `currentPhase` — unknown phases would have crashed the presenter view.

4. **Zero new runtime dependencies — 6th consecutive epic.** Pure CSS bracket layout with connector lines, no charting or animation libraries. The architecture decisions from Epic 1 continue to pay compounding dividends.

5. **Pattern reuse accelerated velocity dramatically.** 3 stories completed in ~3 days (May 5-7). Story 6.1 was slowest (established new patterns), 6.2 and 6.3 were faster due to systematic reuse of SSR pattern, connection badge pattern, socket invalidation matrix, and test helpers.

6. **`roundLabel` DRY extraction timed perfectly.** Deferred from 6.2 ("extract when 3rd consumer appears"), executed in 6.3 when the presenter needed it. Good discipline on "extract when the pattern repeats, not before."

7. **Presenter/MC teleprompter view is a genuine product differentiator.** The dual-device workflow (admin dashboard on laptop + teleprompter on phone) is not offered by competitors and directly addresses the live-event MC use case.

## What Was Challenging / Recurring Struggles

1. **Edge-case visual states consistently missed on first pass (3/3 stories).**
   - 6.1 M4: Empty state missing pulse indicator per AC #6.
   - 6.2 H1: `MatchupCard` hardcoded `isBye={false}` for slot B, hiding bye indicators.
   - 6.3 M3: Completed phase rendered blank when champion data was pending.
   - **Root cause:** Dev agents consistently nail the happy path and data flow but miss transitional/loading/empty visual states. This is a systematic gap, not a per-story issue.

2. **Ad-hoc calculations bypassing established helpers (2/3 stories).**
   - 6.1 M1: Used `parseFloat().toFixed(2)` instead of `sumScores()` for group breakdown totals.
   - 6.3 M1: Used `idx + 1` instead of `entry.rank` for standings display.
   - **Root cause:** When the canonical helper exists but the inline shortcut "looks right," dev agents reach for the shortcut. Needs explicit reminder in project-context.md.

3. **Test gaps for edge-case behaviors (2/3 stories).**
   - 6.1 M2: Missing rate limit test for `getPublicNextMatchups`.
   - 6.1 M3: Missing disconnected-state test for client island.
   - 6.3 M4: Missing connection status opacity wrapper tests.
   - Dev agents write happy-path tests but miss defensive/failure-mode coverage.

4. **No deep manual venue testing done.** All manual verification was in dev environment. Real venue conditions (projector resolution, Wi-Fi drops, concurrent phone loads, Clerk auth in production) remain untested.

5. **No production deployment yet.** Carried from Epic 1. Some classes of issues (real WebSocket fan-out latency, real Postgres advisory lock contention, real Clerk JWT round-trips) only surface against real infrastructure.

## Breakthrough Moments

1. **SSR runtime decision in Story 6.1** — Choosing the HTTP-fallback path over `appRouter.createCaller()` was the right architectural call. It keeps the API runtime sealed inside `apps/api`, avoids NestJS DI bootstrap conflicts in the Next.js runtime, and proved clean enough that Story 6.2 reused it without modification.

2. **Pure CSS bracket layout** — Horizontal multi-column on desktop with connector lines via `border-right` + `border-top`/`border-bottom` pseudo-elements. Responsive switch to vertical stacked on mobile via Tailwind `lg:` breakpoint. Zero dependencies, zero complexity.

3. **`broadcastEnrichedStandings` helper (6.1 review fix)** — Consolidated 5 broadcast sites that were calling `computeStandings` without enrichment. First step toward the general `broadcastAfterCommit()` pattern flagged in Epic 5 retro.

4. **Two different dev agents produced consistent quality.** claude-opus-4-7 (6.1) and Claude Opus 4.6 (6.2, 6.3) both followed project conventions, reused established patterns, and produced code that passed adversarial review with similar finding profiles. The `project-context.md` is doing its job as the canonical rulebook.
