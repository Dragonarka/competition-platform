## What Went Well

1. **Architectural discipline held across all 5 stories.** The RLS transaction pattern, factory router pattern, nanoid ID generation, Zod validation, and shared types in `packages/shared` — all established in 2.1 — were reused verbatim in 2.2–2.5. No drift. No copy-paste rot.
2. **Cumulative Dev Notes gotcha stack grew without regressions.** Story 2.1 documented 15 gotchas; 2.5 carried 22. Every re-appearance was a successful prevention, not a new bug. (Next.js 16 async params, no `middleware.ts`, shadcn Button `asChild` incompat, TanStack Query v5 changes.)
3. **Adversarial code review gate caught real issues.**
   - Story 2.2 [H1]: RLS policy missing on `evaluation_criteria` table (child tables need their own policy, not inheritance).
   - Story 2.3 [H1]: TOCTOU race on participant duplicate check — required catching postgres error code `23505` on insert rather than select-then-insert.
   - Story 2.4 [M1]: `setJudgeConfig` forgot to bump `competitions.updatedAt`.
   - Story 2.5 [L1]: Clipboard error feedback missing in one-time reveal card.
4. **Zero new dependencies after Story 2.1.** Stories 2.2, 2.3, 2.4 used only existing workspace packages. Story 2.5 used Node's built-in `node:crypto` — no `uuid`, no hashing library.
5. **Test-per-procedure discipline.** Every new tRPC procedure received a Zod validation test + null-userId `UNAUTHORIZED` test. Predictable coverage. 4 → 39 tests over the epic.

## What Was Challenging / Recurring Struggles

1. **Next.js 16 breaking changes kept re-surfacing.** `params: Promise<{ id }>`, proxy.ts-not-middleware.ts, shadcn Button `asChild` incompat with `@base-ui/react`. Every story's Dev Notes had to re-state these to prevent regression — the knowledge lives in story files, not a single reference doc.
2. **TanStack Query v5 migration friction.** Story 2.3 discovered `onSuccess` was removed from `useQuery`. Story 2.4 hit the `react-hooks/set-state-in-effect` lint rule and had to adopt a **split-component pattern** (`JudgeGroupsManager` loader + `JudgeGroupsForm` inner component keyed by `comp.id`). That workaround is now load-bearing for any form initialized from server data.
3. **Recurring review finding: missing auth tests.** Stories 2.2, 2.3, 2.4, 2.5 each had a code-review finding flagging missing `null userId → UNAUTHORIZED` tests for newly-added procedures. The pattern is well-understood — it still slips past initial implementation every time.
4. **`updatedAt` on UPDATE is an easy miss.** Story 2.4 [M1] caught `setJudgeConfig` forgetting to set `updatedAt: new Date()` on the mutation. This will happen again unless we have a systematic check.
5. **No real-DB integration tests.** All 39 tests run against a mocked DB. RLS policies, FK cascades, unique constraints, and the TOCTOU fix in 2.3 are verified by reading code and by adversarial review — not by automated tests.
6. **No Playwright E2E tests yet.** The full create-competition → add-criteria → add-participants → configure-judges → generate-links flow has no end-to-end test. Epic 3 (WebSockets + offline queue + real-time) will make this gap more painful.

## Breakthrough Moments

1. **`getCompetition` procedure was born out of a code-review fix in Story 2.3 [M4]** — replaced over-fetching `tournament.list`. Now a core read API used by 2.4 (judge config) and 2.5 (judge links). A review fix became infrastructure.
2. **Public `t.procedure` pattern for judge token validation (Story 2.5)** — establishes how any judge-facing endpoint in Epic 3 (score submit, vote submit) will authenticate: input token → SHA-256 → table lookup, no RLS context, no organizer auth. Clean separation from the `protectedProcedure` organizer-tenant path.
3. **Ownership-by-subquery DELETE pattern** (2.2 → 2.3 → 2.5) — `DELETE WHERE id = X AND competition_id IN (SELECT id FROM competitions WHERE organizer_clerk_id = $user) RETURNING id`. Defense-in-depth on top of RLS. Reused 3 times without modification.
4. **SHA-256 token hashing with raw-token-returned-once UX (Story 2.5)** — `token_hash` column stores SHA-256, raw token only returned at creation in the `generateJudgeLinks` response. The one-time reveal card in the UI makes the security model clear to the organizer.

   - Owner: Dev agent (enforced during `bmad-bmm-dev-story`)
   - Success criteria: no Story 3.x adversarial review re-flags missing auth test, missing `updatedAt` on UPDATE, or missing Zod coverage
   - Checklist items: null-userId UNAUTHORIZED test, Zod validation test, `updatedAt: new Date()` in any UPDATE `.set()`, ownership-via-subquery for any DELETE by id

2. **Consolidate project gotchas into a single reference doc.**
   - Action: run `/bmad-bmm-generate-project-context` to create `project-context.md` (confirmed absent in current tree)
   - Success criteria: all 22 gotchas from Story 2.5 Dev Notes are in one file; Story 3-4's Dev Notes can reference it instead of re-listing
   - Why: Dev Notes are story-scoped; when they're the only source of a rule, there's risk of divergence or forgetting

### Technical preparation for remaining Epic 3 stories

3. **Set up integration test framework against real Postgres before Story 3-5.**
   - Action: consider `/bmad-tea-testarch-framework` (Murat / Test Architect)
   - Why: Story 3-5 (offline queue + Service Worker + reconnect) will have bugs that unit tests with mocked DB cannot catch. RLS, FK cascades, unique constraints, and WebSocket reconnect semantics need a real DB + real browser runtime.
   - Not critical path for 3-4, but strongly recommended before 3-5.

4. **Set up Playwright E2E for the organizer happy path once 3-4 is done.**

   - Scope: create competition → add criteria → register participants → configure judges → generate links → start phase → submit scores → see leaderboard update.
   - Why: this flow crosses 5 Epic 2 stories + 2 Epic 3 stories; there's no test that exercises it end-to-end.
