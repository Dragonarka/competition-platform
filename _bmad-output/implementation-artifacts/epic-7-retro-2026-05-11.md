## What Went Well

1. **"No special branches" architecture held end-to-end.** Story 7-2's most important AC was that simulation must use _identical_ code paths to live — the only differentiation is data. We met this by lifting the `!soloMode` guard to `!soloMode && !isSimulation` and introducing a single helper (`resolveOrganizerJudgeSession`) that branches on `mode` only for session lookup. Scoring, aggregation, advancement, bracket generation, tally, and broadcast all execute the same code regardless of `isSimulation`. Story 7-3 reinforced this — `submitScore`/`submitVote` (the public judge endpoints) needed zero changes for FR55 because they never filtered on `isSimulation` in the first place.

2. **Pre-creating sim sessions at `startCypherPhase` was the right call.** Story 7-2 had a real fork in the road: create sim judge sessions lazily on first score, or pre-create them at phase start. We chose pre-create. This kept the `competition.started` event payload byte-identical to live (with full `judgeAssignments` populated), kept round-robin assignment deterministic, and meant downstream code never had to learn about "missing judges that materialise later." The trade-off (small upfront cost during phase transition) was overwhelmingly worth it.

3. **Append-only events held under destructive operations (Story 7-3).** The reset is a deeply destructive operation (DELETEs across 4 tables). The temptation to also wipe the `events` table was real, but resisting it preserved the architectural rule (events are append-only) AND satisfied AC #5 (auditable simulation history). The `listSimulationResetEvents` query and history panel are a direct payoff — every reset's deletion counts are queryable forever.

4. **Helper extraction at the right moment.** `resolveOrganizerJudgeSession` was extracted in Story 7-2 — exactly when a third call site (simulation cypher + simulation battles + legacy solo) appeared. Same discipline as Epic 6's `roundLabel` extraction: "extract when the pattern repeats, not before." Same lesson, applied consistently.

5. **Story 7-1 adversarial review caught both architectural issues before merge.** H1 (`setState`-in-render anti-pattern in the create form) and M1 (`SimulateConfigLink` always visible regardless of config existence) were both caught and resolved during review. The split-component pattern fix from H1 became precedent we explicitly applied to Story 7-2's `SimulationClient` redirect logic and Story 7-3's reset panel — the lesson propagated immediately.

6. **Mock participants strategy paid off.** Story 7-1's choice to generate mock participants with `SIM-NN` participant IDs and `"Competitor NN"` zero-padded names made simulation data instantly identifiable in the database AND naturally sortable in the standings/presenter views. Story 7-2 and 7-3 inherited this for free.

7. **Reset semantics table forced the right thinking up front.** The dev notes for Story 7-3 included an explicit table of what survives a reset vs. what gets wiped (competitions: UPDATE, criteria: KEEP, competitors: KEEP, judge_sessions: KEEP, scores/votes/matchups/assignments: DELETE, events: APPEND). Writing this down before implementation prevented the "what about competitors?" / "what about real judge tokens?" ambiguities that would have surfaced mid-coding.

8. **Zero new runtime dependencies — 7th consecutive epic.** Pure feature work using existing patterns. Even the new simulation route reuses `StartCypherPhasePanel`, `CypherResultsPanel`, `BracketViewPanel`, `TieResolutionBanner`, and `JudgeVoteInput` — composition, not duplication.

9. **Pattern reuse across the epic.** Story 7-1's split-component pattern (H1 review fix) → applied to 7-2 `SimulationClient` and 7-3 reset panel. 7-1's `SIMULATION` amber badge visual language → applied to 7-2 simulation header banner and 7-3 judge "PRACTICE MODE" badge. 7-2's `SimulationClient` phase-aware composition → extended by 7-3 with reset and history panels. Three stories, one coherent design language.

## What Was Challenging / Recurring Struggles

1. **Adversarial review gate slipped after Story 7-1.** Story 7-1 had a formal `/bmad-bmm-code-review` pass producing 1 HIGH + 3 MEDIUM + 2 LOW findings, all resolved before merge. Stories 7-2 and 7-3 had no equivalent formal review — they went straight from `review` to `done` based on dev-side self-validation. Epic 6's retro explicitly committed: _"Keep the adversarial review gate. 3 HIGHs caught in 3 stories across Epic 6. Non-negotiable."_ That commitment was broken in Epic 7. This is the biggest process gap of the epic.

2. **Real-DB integration test framework was not built.** Epic 6 retro flagged this as critical for Story 7-2 specifically: _"Story 7-2's concurrent role-switching is the textbook scenario for race conditions that only real-DB tests catch."_ Story 7-2 was implemented and shipped without real-DB tests. The mocked-tx tests caught the shape of the helper's logic but cannot validate advisory-lock behaviour under actual concurrency, RLS interaction with the new sim-session creation path, or the `23505` retry path for the `simulation.reset` event sequence. We are flying blind on a class of bugs that may only surface in production.

3. **Two test-spec issues introduced when adding new components.** Both manifested as quick fixes during the dev cycle but exposed a systematic gap:
   - 7-2 `simulation-cypher-panel` test for "submit with selected indices" silently passed `mutate.toHaveBeenCalled()` as a zero-call because `numberInput.value = '7.5'` doesn't fire React's controlled `onChange`. Required the `nativeInputValueSetter` trick documented in `create-competition-form.spec.tsx`. We re-discovered the trick instead of reaching for the documented pattern.
   - 7-3 `simulation-client.spec.tsx` regressed when new child panels (`SimulationResetPanel`, `SimulationHistoryPanel`) were added — the test mocks didn't include them, causing render failures. The mocked-children pattern (`vi.mock('@/components/admin/...', ...)`) needs to be updated every time a new child is added to a parent under test. Easy to miss.

4. **Story 7-3 spec's Task 9 (per-hook socket integration) was implemented partially.** The spec called for `onSimulationReset` to be wired into `useAdminSocket`, `useJudgeSocket`, and `usePublicSocket` with downstream invalidation in admin/judge/public views. The hooks themselves got the callbacks added (good), but consumers were not all wired up — only the judge page got the invalidation hook. The user then added the admin-side wiring manually (visible in the linter-applied diff to `simulation-client.tsx`). Public bracket/standings pages still don't react to `simulation.reset` broadcasts, so spectators see stale data after a reset until they refresh manually. Incomplete vs. spec.

5. **Pre-existing `(admin)/layout.tsx` Clerk-API typecheck error continued to be waived across 3 epics now.** First waived in Story 7-1, again in 7-2, again in 7-3. It's a real type-level bug (Clerk's `auth()` returns `Promise<SessionAuthWithRedirect>` in Next.js 16; we read `.userId` synchronously) that has been pushed forward through every epic. CI hides it via `--filter`, but it will eventually bite (either at runtime or when CI is tightened).

6. **Story 7-2 was very large (33 new tests across 12 tasks).** The dev cycle was successful but the scope was at the upper end of what should be one story. Story 7-3 had 13 tasks. These were borderline cases that could have been split. The dev cycle handled them, but a less capable agent or a noisier context might have struggled.

7. **`is_simulation` flag not surfaced in public-facing data.** Public standings and bracket pages don't display the SIMULATION badge or filter simulations from a "discover" listing. Story 7-1's dev notes explicitly punted this as "future concern" and Story 7-3 didn't revisit it. If real judges open a simulation's public URL to practice, they see no signal that it's not a live competition. The judge view itself does show PRACTICE MODE (7-3), but the public spectator surfaces don't. Minor but worth noting.

## Breakthrough Moments

1. **Helper-with-mode discriminator pattern (Story 7-2).** `resolveOrganizerJudgeSession({ mode: 'solo' | 'simulation-cypher' | 'simulation-battles', ... })` is a clean expression of "same shape, different identity resolution." It satisfies the "no special branches" architectural rule while still allowing each mode to derive its own label and advisory-lock key. This pattern (single helper, mode-based session derivation, all downstream code unaware) is reusable for any future "act-as-someone-else" feature.

2. **Sim-judge label namespace decision (Story 7-2).** Initial design used `Sim Judge G{A-Z}-J{N}` for both cypher and battles. The open question flagged in the spec was whether the `B` for battles could be confused with `GB` (Group B). The implementation chose `Sim Judge BAT-J{N}` for battles — unambiguous, future-proof. Small decision, but the kind of detail that costs hours when it bites later.

3. **Reset semantics table as design tool.** Writing the "what survives vs. what gets wiped" table in Story 7-3's spec _before_ implementation surfaced two non-obvious decisions: (a) keep `judge_sessions` so real-judge training tokens survive resets, (b) keep `events` so audit history compounds across resets. Both decisions held through implementation without revisiting.

4. **Inline-confirm UX inheritance.** Story 7-3's reset panel used the inline two-step confirm/cancel pattern from `score-override-form` (Epic 4). Story 7-3 didn't need to invent destructive-action UX — it inherited it. The shared design language is paying compounding dividends, same as the technical architecture.

5. **`broadcastSimulationReset` to all rooms.** Mirroring `broadcastBracketAdvanced`'s "admin + public + every per-judge room" fanout was the right call. When a sim resets, every connected surface (organizer dashboard, projected public bracket on a second screen, real judges practicing on their phones) needs to know. This kept the cross-device demo flow (Elena's "dual-device" persona from the UX brief) working without per-surface polling.

### New characteristics for Epic 8

- **Single largest cross-cutting refactor in project history.** Every component in `apps/web` becomes a translation key consumer. There is no precedent in this project for a change with this fanout.
- **First runtime dependency added in 7 epics.** `i18next` (or whatever framework is chosen — probably `next-intl` for Next.js 16 compatibility) will end the no-new-deps streak. Worth flagging.
- **Error-code-to-message mapping required.** All `ErrorCodes` from `packages/shared/errors` need translation keys (per Story 8-1 AC). This pulls error-handling concerns into the i18n layer.
- **CI key-parity check needed.** Story 8-1 AC explicitly requires `en.json` and `es.json` parity enforcement. New CI gate.
- **Storage split for preferences.** Authenticated users → user profile (which doesn't exist yet — there's no `users` profile table in the DB schema). Judges → localStorage. Public spectators → localStorage. Story 8-2 may need a new DB column on `users` or a separate `user_preferences` table.

### Architectural assumptions to revisit before Epic 8 starts

- **There is no users profile table.** `packages/db/schema/users.ts` exists — verify if it has a `preferences` field or similar. If not, Story 8-2 may need a migration.
- **`@base-ui/react` (NOT Radix) i18n story.** The shadcn-style components are built on `@base-ui/react`. Confirm i18n integration story before picking the framework. Some components may need replacing.
- **Tremor charts (admin dashboard) i18n.** Story 8-2 AC explicitly calls out Tremor chart legends. Tremor 3.x has its own i18n surface — verify before committing.
- **Format-plugin string ownership.** Strings inside `packages/formats/cypher-battles/*` (e.g., `JudgeVoteInput`, `JudgeScoreInput`) need to be considered: do format plugins own their strings, or do they receive them via props from the platform? This is a Day-1 architecture decision (per the saved memory: "Format Plugin Architecture — pluggable, domain-agnostic, open-source modules with custom UI") that needs revisiting.

### One possible scope adjustment

Story 8-1's AC says "no hardcoded strings exist anywhere in `apps/web`." This is **enforceable only with a CI rule**. If a CI lint rule for hardcoded strings is not part of the story, the AC is aspirational and will rot the moment Story 8-2 ships. Consider explicitly adding the lint rule to Story 8-1's tasks.
